## 0. Why this is not "just a settings path"

Read before touching anything.

- Today plugin discovery is **build-time**: `frontend/src/plugins/discovery.ts` does
  `import.meta.glob("./*/manifest.tsx", { eager: true })` and freezes the result into a
  module-level `PLUGINS` constant. Every derived map (`viewRegistry`, `tabDefinitions`,
  `tabById`, `tabCatalog`, `defaultTabIdByPlugin`, `PLUGIN_IDS`, `OPTIONAL_PLUGIN_IDS`,
  `SYSTEM_PLUGIN_IDS`) is a module constant computed at import time in
  `frontend/src/plugins/catalog.ts` / `registry.ts`. A runtime-added plugin cannot appear
  in any of these. **Making the plugin set runtime-mutable is the core of Phase 1.**
- The browser cannot read a filesystem folder. The per-user **agent** (already installed
  per machine, already has FS access, already the storage backend for Notebook/Requests)
  reads the folder and serves manifests + built bundles over HTTP. The frontend fetches
  them from the agent base URL.
- The contract **already anticipates external plugins**: `PluginOrigin.LOCAL`
  (`frontend/src/constants.ts`), the `mount(ctx: MountContext): Unmount` tab render path
  and the `HostApi` / `MountContext` (`frontend/src/core/plugins/host.ts`, with
  `agentBaseUrl`) exist but are unused. Local plugins render via `mount()` (raw DOM
  container + HostApi), NOT via `element` (ReactNode). This is the isolation boundary:
  local plugins bring their own React and never import host `@/...` internals.

### Scope decision baked into this brief (override in the run prompt if wrong)

- **Local plugins are frontend-only bundles.** Their server needs are met by agent
  endpoints. For Notebook/Requests the agent Python (`agent/app/services/notebook*.py`,
  `requests_*.py`) **stays in the agent** — it is already per-user/local; only its route
  auth changes (Phase 2/3). Dynamically loading Python backends from the folder
  ("full-stack local plugins") is **explicitly out of scope** and noted as a future
  evolution in §7.
- **Local plugins are outside RBAC.** They are never added to `OPTIONAL_PLUGIN_IDS`, never
  seeded into the security catalog, never appear in Profile → Plugins toggles or the
  Security matrix. Visible iff present in the user's folder.

## 1. Terminology & data model (applies to all phases)

- **Global / builtin plugin**: `origin: PluginOrigin.BUILTIN`, compiled in, RBAC-gated,
  optionally in `OPTIONAL_PLUGIN_IDS`. Unchanged behavior.
- **Local plugin**: `origin: PluginOrigin.LOCAL`, discovered at runtime from the agent,
  rendered via `mount()`, RBAC-exempt.

### Local-plugin package layout (`~/Projects/qaa-tms-plugins/<name>/`)

```
<name>/
  plugin.json          # manifest METADATA only (no code)
  dist/index.js        # built ESM bundle; default export = LocalPluginModule (see §4)
  dist/*               # any assets the bundle imports
  src/…                # optional source; agent never reads it
```

`plugin.json` schema (validated by the agent AND re-validated by the frontend):

```jsonc
{
  "id": "notebook",                 // string; must be unique among local plugins
  "label": "Notebook",
  "icon": "notebook",               // builtin IconName OR "./dist/icon.svg" (served by agent)
  "route": "/notebook",             // must start with "/"
  "order": 28,
  "contractVersion": 1,             // must satisfy host SUPPORTED_CONTRACT_VERSION_RANGE
  "requiresAgent": true,
  "entry": "dist/index.js",         // path (within the plugin dir) to the ESM bundle
  "navSection": "primary",          // optional
  "tabs": [
    { "id": "notebook-browse", "title": "Browse", "viewKey": "notebook-browse" },
    { "id": "notebook-search", "title": "Search", "viewKey": "notebook-search" }
  ]
}
```

No `kind` field — local plugins are implicitly OPTIONAL-like but RBAC-exempt; the frontend
sets `kind` internally. No `adminOnly` (irrelevant off-RBAC); if present, ignore it.

## PHASE 1a — Make the frontend plugin registry runtime-mutable (pure refactor, no behavior change)

Goal: builtin plugins keep working exactly as today, but the set of plugins and every map
derived from it become a **runtime store** that can later receive local plugins. Zero
behavior change; all existing tests pass; new tests prove the store equals today's
constants when no local plugins are present.

### Files

- `frontend/src/plugins/discovery.ts`: keep the build-time glob, but export the builtin
  set as `BUILTIN_PLUGINS` (rename `PLUGINS` → `BUILTIN_PLUGINS`; add a
  `export const PLUGINS = BUILTIN_PLUGINS` alias only if needed to avoid a giant churn —
  prefer updating imports).
- New `frontend/src/plugins/pluginRegistryStore.ts` (Zustand, matching the existing store
  style under `frontend/src/store/`): holds `plugins: PluginManifest[]` (initialized to
  `BUILTIN_PLUGINS`) plus a `setLocalPlugins(local: PluginManifest[])` action that
  recomputes `plugins = [...BUILTIN_PLUGINS, ...local]` (sorted the same way
  `validatePluginManifests` sorts: by `order`, then `id`). Derive and memoize the maps
  (`viewRegistry`, `tabDefinitions`, `tabById`, `tabCatalog`, `defaultTabIdByPlugin`) as
  selectors off `plugins`, using the exact builder logic currently in
  `catalog.ts`/`registry.ts`.
- `frontend/src/plugins/catalog.ts` & `registry.ts`: the pure functions
  (`pluginVisible`, `visiblePlugins`, `tabVisible`, …) stay pure but take `plugins` as
  input (or read the store). The module-level constant maps become store selectors.
  Provide hook wrappers (`usePlugins()`, `useViewRegistry()`, `useTabDefinitions()`, …)
  for React consumers; keep non-React callers working via `getState()` accessors.
- `frontend/src/plugins/provider.tsx` / `context.ts`: `PluginsProvider` reads `plugins`
  from the store instead of the frozen `PLUGINS` import.
- Update every importer of the old constants to the store/hook equivalents
  (`host.ts` uses `pluginById`/`tabDefinitions`; `Workspace.tsx`, `Sidebar.tsx`,
  `AppLayout.tsx`, `routes.tsx`, admin/security, etc.). The footprint is wide but
  mechanical.

### Constraints

- **No behavior change.** With no local plugins, `usesPlugins()` ⇒ `BUILTIN_PLUGINS`, and
  every derived map is byte-identical to today's constant. Add a test asserting this.
- Keep `validatePluginManifests` and `definePlugin` validation; run the same uniqueness
  checks (`id`, `route`, `tabId`, `viewKey`) across the merged set, and on collision
  **drop the local plugin with a `console.warn`**, never the builtin (fault isolation).
- `eslint`, `tsc --noEmit`, `vitest` all green. See
  `reference_verification_commands` memory for exact commands.

### Acceptance

- All existing frontend tests pass unchanged (except mechanical import updates).
- New unit test: store initialized ⇒ `plugins === BUILTIN_PLUGINS` and derived maps equal
  the previous constants.
- New unit test: `setLocalPlugins([...])` merges, sorts, and dedupes (builtin wins on
  collision).

## PHASE 1b — Agent: local-plugins folder setting + scan + serve

Goal: the agent exposes local plugins found in a configured folder.

### Setting (Profile → Settings surface)

- Add `EnvKey.LOCAL_PLUGINS_DIR` (env var `AGENT_LOCAL_PLUGINS_DIR`) in
  `agent/app/core/constants.py`; add `local_plugins_dir: str | None` to `Settings`
  (`agent/app/core/config.py`), default empty/None (feature off).
- Register it in `AGENT_SETTINGS_ENV_KEY_BY_FIELD`
  (`agent/app/api/routes.py`, ~line 295) and in `AgentSettingsRead`/`AgentSettingsUpdate`
  (`agent/app/schemas.py`, `to_agent_settings_read`) so it round-trips through the existing
  settings PATCH → `.env` write path (same mechanism as `kubeconfig`, `staging_bin`).
- Frontend Profile → Settings: add a text field for the folder path under a new
  "Local plugins" (or "Companion") settings section. (Verify the Profile settings form
  location — likely `frontend/src/plugins/profile/…`; wire it like existing agent-settings
  fields.)

### Service + routes (`agent/app/services/local_plugins.py`, routes in `routes.py`)

- `GET {AgentPath.PLUGINS}` (add `AgentPath.PLUGINS = "/plugins"`): if
  `local_plugins_dir` is empty/missing/unreadable ⇒ return `{ "plugins": [] }` (never 500;
  the feature is optional). Otherwise scan **immediate subdirectories**; for each with a
  readable `plugin.json`:
  - Parse + validate against the §1 schema (id/label/icon/route/order/contractVersion/
    entry/tabs; route starts with `/`; contractVersion supported; entry path stays inside
    the plugin dir). On invalid: **skip that plugin**, add a structured warning to the
    response (`{ "warnings": [{ "dir": "...", "error": "..." }] }`), never fail the whole
    request.
  - Enforce **unique `id`** across the returned set; on dup, skip the later one with a
    warning.
  - Return metadata + a resolved `entryUrl` (relative path the frontend appends to the
    asset route, e.g. `/plugins/<id>/assets/dist/index.js`).
- `GET {AgentPath.PLUGINS}/{plugin_id}/assets/{path:path}`: serve a static file from the
  plugin dir. **Path-traversal guard**: resolve the requested path, assert it is within
  `local_plugins_dir/<plugin_id>/`; 404 otherwise. Correct `Content-Type` (`.js` ⇒
  `text/javascript`, `.svg`, `.css`, …). This is how the browser loads the ESM bundle,
  the icon, and assets.
- **Auth**: both routes use `require_auth` only — **no `require_permission`**. Local
  plugins are RBAC-exempt by design (the authenticated portal user on their own machine).
- CORS: local plugin assets are fetched cross-origin from the agent like every other
  agent call — reuse the agent's existing CORS handling (see `project_cors_env_bug`,
  `environment_agent_port_collision` memories; the agent already serves the portal origin).

### Constraints / acceptance

- `ruff`, `mypy app`, `pytest` green (per `reference_verification_commands`).
- Tests: empty/missing dir ⇒ `[]`; one valid plugin ⇒ returned; one invalid `plugin.json`
  ⇒ skipped + warning, valid siblings still returned; duplicate id ⇒ one skipped;
  asset route serves a file and **rejects `../` traversal** (400/404, never escapes dir).

## PHASE 1c — Frontend: load, render, and RBAC-exempt local plugins

Goal: when the agent is reachable and returns local plugins, they appear in the sidebar
and their tabs render via `mount()`; they are exempt from RBAC.

### Loader (`frontend/src/plugins/localPlugins.ts`)

- After auth + agent detection (reuse the companion/agent-base-url plumbing —
  `useCompanionStatus`, `MountContext.agentBaseUrl`, the agent ports resolution in
  `frontend/src/core/runtimeConfig.ts`), fetch `GET {agentBaseUrl}/plugins`.
- For each returned manifest, `import(/* @vite-ignore */ new URL(entryUrl, agentBaseUrl).href)`
  to load its ESM module (§4 shape). Build a `PluginManifest` with `origin: LOCAL`,
  `kind: PluginKind.OPTIONAL`, and **`mount`-based tabs**: each tab's `mount` delegates to
  the loaded module's `mount(viewKey, ctx)`.
- Validate each with the same `definePlugin`/`validatePluginManifests` rules before
  registering; on failure warn + skip (fault isolation — one bad plugin never blanks the
  portal). Enforce contractVersion via `isSupportedContractVersion`; unsupported ⇒ hide
  with a console warning.
- Call `pluginRegistryStore.setLocalPlugins(loaded)`; the sidebar re-renders when they
  arrive. Re-run on agent-base-url change / manual reload.

### Rendering `mount()` tabs

- Add `<MountedView tab={…} agentBaseUrl={…} />` (or extend the existing Workspace view
  renderer) that: creates a container `div`, builds a `MountContext` from the live
  `HostApi` (`useBuiltinHostApi()`) + `agentBaseUrl`, calls `tab.mount(ctx)` on mount, and
  invokes the returned `Unmount` on unmount / viewKey change. Builtin `element` tabs keep
  their current React rendering path; only `mount` tabs use this.
- Verify the Workspace tab renderer (`frontend/src/app/layout/Workspace.tsx` +
  `viewRegistry`) branches on `pluginTabHasElement(tab)` vs `pluginTabHasMount(tab)`.

### RBAC exemption

- `pluginVisible` (`catalog.ts`): if `plugin.origin === PluginOrigin.LOCAL` ⇒ visible
  (skip `enabledOptionalIds` membership and `pluginPermitted`). Still require a logged-in
  user.
- Local plugin ids are **never** added to `OPTIONAL_PLUGIN_IDS`, Profile → Plugins
  toggles, or the Security matrix. Confirm Profile → Plugins and Admin → Security iterate
  only builtin/`OPTIONAL_PLUGIN_IDS`, not the merged set — adjust if they read the merged
  store.

### Acceptance

- With the agent returning a stub local plugin, it shows in the sidebar for a
  no-permissions user (proves RBAC exemption) and its tab renders through `mount()`.
- A local plugin whose bundle throws on import is skipped; the rest of the portal is fine.
- No agent / empty folder ⇒ portal identical to today.
- `eslint` + `tsc` + `vitest` green.

## 2. SDK for external plugin authors (`frontend/` → publishable `sdk/`)

So `~/Projects/qaa-tms-plugins/*` can be built without importing host `@/...` internals:

- Extract a tiny **plugin SDK** (a `sdk/` package or a generated `plugin-sdk.d.ts` +
  runtime helper) exposing: the manifest metadata types, `HostApi` / `MountContext` /
  `ThemeTokens` / `Unmount`, `CONTRACT_VERSION` + `isSupportedContractVersion`, and a thin
  typed agent-fetch helper (base URL + auth header from `MountContext`).
- The SDK carries **no host React** — local plugins bring their own React and render into
  `ctx.container`. This is what keeps them decoupled and per-user-swappable.
- Provide a minimal example plugin + a `build` recipe (tsup/Vite lib mode → `dist/index.js`
  ESM) as the template users copy into `~/Projects/qaa-tms-plugins`.

### §4 — LocalPluginModule contract (what `dist/index.js` default-exports)

```ts
export interface LocalPluginModule {
  contractVersion: number;
  // Render the given viewKey into ctx.container; return a cleanup fn.
  mount(viewKey: string, ctx: MountContext): Unmount;
}
export default myPluginModule;
```

The metadata (id/label/icon/route/order/tabs) lives in `plugin.json` (read by the agent);
the code module only needs `mount`. Keep the two in sync in the template.

## 7. Explicitly out of scope (future evolution)

- **Full-stack local plugins** (agent dynamically loading Python route handlers from the
  folder). Today Notebook/Requests server code stays compiled into the agent (dead-but-
  inert on machines that don't use them; auth-gated). Making the *backend* also load from
  the folder is a separate, larger design (dynamic import + route registration + sandbox).
- **Sharing/distributing** local plugins between users (a marketplace). Each user's set is
  independent by construction (their agent, their folder) — no central registry.
- Host-level features a builtin plugin drives that a `mount()` plugin can't yet (e.g. the
  Notebook sidebar reminder badge) — either dropped or later exposed via a HostApi channel.
